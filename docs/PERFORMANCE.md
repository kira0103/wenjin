# 入库性能优化记录

记录 2026-11-03 E5 全量向量化期间的本机优化过程、取舍和可复现参数。目标是在单机、单 GPU、本地 PostgreSQL/pgvector 条件下缩短入库时间，并让 GPU 持续有活干。

## 环境与数据

- Windows 11，Ryzen 7 7700X，32 GB RAM
- NVIDIA GeForce RTX 4070 Ti 12 GB
- 本机 PostgreSQL 17 + pgvector 0.8.7（`build/postgres` 托管）
- 模型：`intfloat/multilingual-e5-large`，1024 维，fp16 副本，CUDAExecutionProvider
- 批次：3,882 篇文献，约 269 万块，合计约 10.35 亿字符
- 优化期间暂时移除 1024 维 HNSW，只保留堆表、关键词和 GIN 索引；结束后一次性重建

## 原始性能（单 Worker、逐篇串行）

| 指标 | 数值 |
| --- | --- |
| 文档处理方式 | 1 篇文档一个任务，串行执行 |
| GPU 平均利用率 | 34–38% |
| GPU <10% 空闲采样 | 约一半（31/60） |
| 阶段占比 | 嵌入约 61%，写库约 26%，切分约 13% |
| 完成吞吐 | 约 36.5 块/秒 |
| 预计全量嵌入耗时 | 约 20 小时（按 269 万块外推；早期按嵌入上限的乐观估计为 12–13 小时，未计入大量小文档的固定开销） |

GPU 空闲的根因是单篇流水线严格串行：切分（CPU）→ 嵌入（GPU）→ 写库（DB）→ 下一篇，GPU 在 CPU 和数据库阶段完全等待。

## 优化过程

### 1. 批量入库与索引维护（基线）

- 入库期间不增量维护 HNSW，全部完成后一次 `CREATE INDEX`；
- 写入语句时限 600 秒、锁等待 60 秒、整篇写入预算 3600 秒；
- 数据库自动调参（shared_buffers、maintenance_work_mem、checkpoint 等）；
- `quality_api` 在大表上不再做精确 `count(*)`，避免批量期间状态页面每几秒超时。

这一层是后续并发的前提：没有 HNSW 增量写，单篇写库成本才降得下来。

### 2. 文档级并发：1 → 4

4 个文档任务同时处理，GPU 嵌入、切分和写库互相重叠。

| 指标 | 实测 |
| --- | --- |
| 吞吐 | 73.7 块/秒 |
| GPU 平均利用率 | 61.8% |
| GPU 空闲采样 | 5/60 |
| 相对原始 | 约 2.0 倍 |

### 3. 跨文档拼批 + 预取（保留自适应部分）

- 小文档的 batch 经常是 4–20 条，GPU 批次填不满；
- 将多个并发文档的批次送进统一队列，由 batcher 合并；
- 固定 100ms 窗口版本会造成“等窗口→爆发”的脉冲，实测 4 分钟吞吐在 97/53/13 块/秒之间大幅波动，GPU 标准差约 26；
- 最终保留**自适应窗口**：只有当前请求不足 16 条时才等待最多 50ms，正常 32 条请求立即执行；
- 文档内预取 4 批，避免文档在切分/写库时 GPU 队列见底。

这一层单独使用时平均提升有限，但为最终的 CPU/GPU 重叠准备好了请求队列。

### 4. 两路并发 ONNX 推理（最终关键一步）

fastembed 默认在同一线程里串行做 tokenize 和 ONNX 推理。即使队列里有请求，GPU 仍会在下一批 tokenize 时空闲。

最终方案：

- 2 个 batcher worker 同时消费队列；
- `models.embed` 用容量 2 的信号量替代独占锁，允许 2 个 ONNX 调用同时执行；
- 一个调用在 GPU 推理时，另一个调用在 CPU tokenize；GPU 队列始终有活；
- 仍然只有**一份模型权重**驻留显存，不复制模型。

实测 4 分钟窗口：

| 指标 | 数值 |
| --- | --- |
| 完成吞吐 | **186.8 块/秒** |
| GPU 平均利用率（120 秒采样） | **99.4%** |
| GPU 利用率标准差 | **4.2** |
| GPU 0–10% 低谷采样 | **0/120** |
| GPU ≥90% 采样 | **118/120** |
| 相对上一版 | 约 2.0 倍 |
| 相对原始 | **约 5.1 倍** |

## 最终配置

| 环境变量 | 最终值 | 作用 |
| --- | --- | --- |
| `SHIXUE_INGEST_CONCURRENCY` | `4` | 同时处理的文档数 |
| `SHIXUE_EMBED_PREFETCH` | `4` | 每篇文档提前提交的嵌入批次数 |
| `SHIXUE_EMBED_WORKERS` | `2` | batcher 消费者线程数 |
| `SHIXUE_EMBED_INFLIGHT` | `2` | 同时执行 ONNX 推理的调用数 |
| `SHIXUE_EMBED_BATCH_TEXTS` | `32` | 拼批上限（两个内部 16 块批次） |
| `SHIXUE_EMBED_BATCH_WINDOW_MS` | `50` | 仅小批次使用的合并窗口 |

启动示例：

```powershell
npm stop
$env:SHIXUE_INGEST_CONCURRENCY = '4'
$env:SHIXUE_EMBED_PREFETCH = '4'
$env:SHIXUE_EMBED_WORKERS = '2'
$env:SHIXUE_EMBED_INFLIGHT = '2'
npm start
```

## 总提升

| 指标 | 原始 | 最终 | 变化 |
| --- | --- | --- | --- |
| 入库吞吐 | 36.5 块/秒 | 186.8 块/秒 | **5.1 倍** |
| GPU 平均利用率 | 34–38% | **99.4%** | 接近满载且稳定 |
| GPU 低谷采样 | 约一半 | **0%** | 不再出现长时间空闲 |
| 269 万块嵌入耗时 | 约 20 小时 | 约 4 小时 | 约 5 倍 |

## 质量与正确性验证

### 模型选择：E5-large 优于 bge-small

同一批 6 篇文献、30 条查询：

| 模型 | Recall@1 | Recall@5 | Recall@10 | MRR |
| --- | --- | --- | --- | --- |
| `multilingual-e5-large` | 0.7667 | 0.9333 | 0.9333 | 0.8444 |
| `bge-small-zh-v1.5` | 0.6000 | 0.6667 | 0.7000 | 0.6190 |

E5 质量明显更高，因此保留 E5；bge-small 只作为快速评测备选。

### fp16 与并发一致性

- fp16 与 fp32 输出：余弦均值 **0.99999832**，最小值 **0.99999734**；
- 2 路并发 ONNX 与串行结果：512 条真实中文文本，余弦最低 **0.999964**、平均 **0.9999987**；
- 4 路并发：加速比反而降到 1.08（2 路为 1.13），余弦最低 0.9999479，因此最终取 2 路；
- 跨文档拼批只合并推理调用，不合并文本、不改变 chunk 边界、所属文献和引用位置，检索粒度与准确性不变。

## 取舍与注意事项

- **为什么不是 8 路文档并发**：最终瓶颈是共享 GPU 会话；GPU 已 99.4%，增加文档槽位只会增加数据库连接、CPU tokenize 和锁竞争。
- **为什么不是 4 路推理**：实测 4 路比 2 路更慢，且会有更多显存/调度抖动。
- **为什么批次上限是 32**：fastembed 内部仍按 16 条一批；32 是两个完整内部批次。更大的拼批不会让 GPU 一次算更多，只会增加排队延迟。
- **为什么窗口只对小批次生效**：固定窗口会让正常 32 条请求也等 50–100ms，形成脉冲；自适应后 GPU 利用率标准差从 26+ 降到 4.2。
- **硬件状态**：满载时约 75°C、244W、显存 8.0/12 GB，属正常范围；如温度或功耗异常，可把 `SHIXUE_EMBED_WORKERS` 和 `SHIXUE_EMBED_INFLIGHT` 调回 1 做串行回退。
- **空文本失败**：少量文献清洗后没有可索引文本，会保持失败状态，不能向量化；不属于性能问题。

## 适用性与迁移到其他模型

这套优化分三层，通用程度不同：

| 层级 | 内容 | 对其他模型的适用性 |
| --- | --- | --- |
| 流水线结构 | 4 个文档并发、每篇预取 4 批、自适应跨文档攒批、一次性批量写库、入库期间推迟 HNSW | **通用**。只要模型提供“给定文本列表返回向量”的本地调用，结构就可以复用 |
| 推理并发 | 2 个 batcher worker + 2 个并发 ONNX 调用 | **依赖运行时**。要求 ONNX/fastembed 会话和 tokenizer 线程安全，且显存允许；换模型必须重新验证 |
| 精度与硬件 | fp16、TF32、batch_size 16/32、50ms 窗口 | **特定于本机与 E5-large**。其他模型可能不支持 fp16，最佳 batch_size、显存上限和窗口也不同，需要重新测 |

迁移到另一款本地 ONNX 模型时建议：

1. 先用小样本（例如 512 条真实分块）对照串行和 2 路并发：向量余弦应接近 1，2 路吞吐应明显高于串行；
2. 观察显存峰值；接近 12 GB 就把 `SHIXUE_EMBED_INFLIGHT` 降为 1；
3. 把 `SHIXUE_EMBED_BATCH_TEXTS` 设为该模型内部 `batch_size` 的整数倍，不要固定照搬 32；
4. 如果模型不支持 fp16 或并发推理，保留“文档并发 + 预取 + 批量写库”即可，仍能拿到 HNSW 推迟和写库阶段的收益；
5. 远程 API 模型（`openai_compatible`）不适用 ONNX 并发结论：并发数受服务商限流、批量上限和超时约束，应以请求配额和延迟为准，不能按 GPU 利用率判断。

简而言之：**“让 CPU、数据库和 GPU 流水线重叠”是通用的；“2 路 ONNX + 8 GB 显存 + fp16”是本机 E5 的调优结果，不是任何模型都能直接复制的固定参数。**

## 监控与回退

- 入库期间可观察 `nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits` 的 1 秒采样；
- 批量入库完成后用 [bulk_vector_index.py](../scripts/bulk_vector_index.py) 的 `status`、`verify` 检查索引；
- 需要保持稳定时可设置：
  - `SHIXUE_EMBED_WORKERS=1`、`SHIXUE_EMBED_INFLIGHT=1`：回到单推理流，吞吐下降但最保守；
  - `SHIXUE_INGEST_CONCURRENCY=2`：减少文档并发和数据库连接压力；
  - `SHIXUE_EMBED_PREFETCH=2`：降低每篇文档的预取深度。
- 索引维护命令和批量入库流程见维护手册的“批量入库与向量索引维护”一节。
